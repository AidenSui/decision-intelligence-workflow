# Acceptance Template: User-Facing Decision Output

This file demonstrates the expected visible output shape without anchoring the workflow to any specific decision domain.

## Sample User Decision

> I am deciding whether to continue with Option A, switch to Option B, or redesign the situation entirely. I have meaningful reasons to continue, but I also see repeated costs and uncertainty. I am not sure whether more time would create useful evidence or simply extend a pattern that may already be clear.

## User Summary

- Recommendation type: `test`
- Recommendation: Do not commit or reject immediately; run a bounded viability test before making a final decision.
- Core reason: The situation may still have remaining value, but more time is only justified if it can produce new evidence.
- Biggest risk or objection: A test can become disguised delay if the standards and stop-loss are vague.
- First action: Within 48 hours, define the minimum conditions that would make continued investment acceptable.

## The Real Decision

The surface question is whether to continue or stop. The more useful question is whether the situation is still viable enough to deserve more time.

The user's discomfort is real information. It should be taken seriously, but it should not be the only input into a high-impact decision.

## Options I See

- Continue without changing the structure: low immediate friction, but likely to preserve the same uncertainty.
- Stop now: clean and possibly correct if disqualifiers or repeated failed attempts are already clear.
- Run a bounded viability test: useful only if it can create new evidence.
- Redesign the option structure: change the terms, constraints, timeline, or stakeholder commitments before deciding.

## Key Judgment

I would not optimize the surface question directly yet, because it may compress the real decision too narrowly.

The key question is:

> Would a bounded test reveal new information, or would it merely extend an already-disproven pattern?

## Viability Check

- Disqualifiers: identify any facts that make further testing inappropriate.
- Prior attempts: check whether this has already repeated through cycles of effort, hope, and relapse.
- Real desire vs avoidance: ask whether the user still wants the upside, or mainly fears the cost of stopping.
- Ownership required: name who or what must change for the situation to improve.
- Non-negotiables: define the minimum conditions required for continuation.
- Remaining value: identify what is still worth preserving, compounding, or repairing.

## Strongest Objection

The strongest objection is that a bounded test may appear disciplined while functioning as delay. If the situation has already failed the same test multiple times, the recommendation should shift away from `test` and toward `reject` or `redesign`.

## Final Recommendation

Recommendation type: `test`

Run a short viability test only if there are no disqualifiers, the prior attempt pattern is not already decisive, the required ownership is plausible, and the remaining value is real.

The bet is: if the situation is viable, a short and bounded test should produce observable evidence. If it does not, the user should not continue investing on vague hope.

## Test Plan

### 48 Hours

- Define the non-negotiable continuation conditions.
- Identify the strongest disqualifier that would make testing inappropriate.
- Write down what new evidence the test must produce.

### 7 Days

- Confirm whether the required ownership or external response is actually present.
- Reduce the test to 2-3 observable criteria.
- Decide the stop-loss before the user is emotionally re-anchored to the status quo.

### 30 Days

- Review evidence, not intentions.
- Decide whether to continue, redesign, or stop.
- Do not extend the test unless the evidence has materially improved.

### Later / Optional

- Add support or structure only if the initial test produces real signal.
- Revisit the option set if the original framing remains too narrow.
- Convert the decision into a longer plan only after viability is established.

## Communication Script

"I want to discuss this without turning it into a verdict conversation. I still see possible value here, but I do not want us to continue on vague hope. I would like us to define what improvement or evidence would actually count. I also want to name the conditions under which we should stop rather than keep extending the same pattern. My goal is not to win the argument; it is to make the next step honest and bounded. If the evidence does not show up, I want us to respect that instead of moving the goalposts."

## Stop Conditions

- Stop if a disqualifier appears.
- Stop if the required ownership or external response is absent.
- Stop if the same failed pattern repeats during the test window.
- Stop if continuing requires violating the user's non-negotiables.

## What Would Make This Wrong

This recommendation would change if the situation already has decisive evidence, if further testing creates unacceptable downside, or if the user no longer wants the upside and is only avoiding the cost of stopping.
